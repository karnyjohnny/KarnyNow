## 1. Verdict

**The presentation path is D3D9 `StretchRect` from an NV12 surface in `D3DPOOL_DEFAULT`,
with linear filtering, into the X8R8G8B8 backbuffer.** The GPU performs both colour-space
conversion and scaling. The CPU never touches pixels. This validates D6 by measurement.

Cost (x64, 200 iterations, high-resolution timing):

| Operation | mean | median | p95 | fps at mean |
|---|---|---|---|---|
| `Present` only | 1.313 ms | 1.298 ms | 1.429 ms | 762 |
| `StretchRect` RGB→backbuffer + `Present` | 2.542 ms | 2.536 ms | 2.622 ms | 393 |
| **`StretchRect` NV12→backbuffer + `Present`** | **2.997 ms** | **2.979 ms** | **3.101 ms** | **334** |
| GDI `SetDIBitsToDevice` (last-resort rung) | 1.947 ms | 1.665 ms | 2.855 ms | 514 |

Against the budgets: 33.3 ms (30 fps) → NV12 path uses **9 %** of the frame interval;
16.7 ms (60 Hz) → **18 %**. Presentation is a non-issue; the CPU decode budget from T1
(24.8 % of both cores at 720p30) stands untouched.

x86 benches show identical means but percentiles quantised to {0, 16, 32} ms — that build's
per-iteration timing fell back to tick granularity. Irrelevant in practice (D8 targets
x64), but noted so nobody trusts x86 p95 numbers.

## 2. What works (all HRESULTs `S_OK` unless stated)

### 2.1 Device and modes

- HAL device creation: **HARDWARE_VERTEXPROCESSING OK**. `SOFTWARE_VERTEXPROCESSING`
  fails with `E_FAIL (0x80004005)` → the client must always create the device with
  hardware vertex processing (and there is no REF fallback: the REF rasterizer does not
  accept NV12/YUY2 at all — see 2.2).
- `TestCooperativeLevel` OK before and after every stretch case; the driver survived the
  whole run apart from the SYSTEMMEM sub-steps (section 3).
- Adapter: PCI `8086:2A42`, `igdumd64.dll`, version hex `0008000F000A0B35` =
  **8.15.10.2869** (matches the documented driver), `Description` = "Intel(R) HD Graphics
  Family" (the name still lies; PCI ID is the truth).
- Current mode: **1280×800 @ 60 Hz, 32 bpp**. Enumerated 1280×800 modes:
  40 Hz/16 bpp, **60 Hz/16 bpp**, 40 Hz/32 bpp, **60 Hz/32 bpp**. The 40 Hz entries are
  the Intel DPST/battery modes — they exist, they are not active, and the user has
  committed to keeping 60 Hz (open question Q1 answered). D9 stands unchanged: the client
  measures the interval between `Present` calls and never assumes a rate.
- `StretchRectFilterCaps = 0x03000300` = `MINFPOINT|MINFLINEAR|MAGFPOINT|MAGFLINEAR`,
  `DevCaps2 = 0x51` (incl. `CAN_STRETCHRECT_FROM_TEXTURES`), VS 3.0 / PS 3.0,
  max texture 4096×4096, `PRESENT_INTERVAL_IMMEDIATE` available.
  **Harness bug (cosmetic):** the summary printed `srf_point=false srf_linear=false` —
  the harness tested the wrong mask bits. Correct constants: `MINFPOINT 0x00000100`,
  `MINFLINEAR 0x00000200`, `MAGFPOINT 0x01000000`, `MAGFLINEAR 0x02000000`. The
  functional probe settles it anyway: `StretchRect` with `D3DTEXF_LINEAR` returned `S_OK`
  in every backbuffer case. Production code should prefer the functional probe over caps
  bits (lesson #7: do not trust a reported capability you have not exercised).

| Surface | Create | `LockRect(D3DLOCK_NOSYSLOCK)` | Pitch |
|---|---|---|---|
| NV12 DEFAULT 960×540 | OK | **OK** | **960** (= width, as expected) |
| NV12 DEFAULT 1280×800 | OK | OK | 1280 |
| YUY2 DEFAULT 960×540 | OK | OK | 1920 |

Locking DEFAULT-pool NV12 works because this is Intel UMA: "video memory" is stolen system
RAM. **The decoder will write directly into a lockable DEFAULT NV12 surface** (pitch =
width here, but code must always honour the returned pitch).

### 2.5 `StretchRect` cases (functional, both x64 and x86 identical)

| Case | Conv-check | `D3DTEXF_LINEAR` | `D3DTEXF_POINT` |
|---|---|---|---|
| X8R8G8B8 960×540 → backbuffer (scaled) | allowed | **S_OK** | S_OK |
| YUY2 960×540 → backbuffer (scaled) | allowed | **S_OK** | S_OK |
| NV12 960×540 → backbuffer (scaled) | allowed | **S_OK** | S_OK |
| NV12 1280×800 → backbuffer (1:1) | allowed | **S_OK** | S_OK |
| NV12 → X8R8G8B8 **offscreen plain surface** | allowed | **`D3DERR_INVALIDCALL` (0x8876086C)`** | not attempted |

The last row is a real constraint: **format conversion works only when the destination is
the backbuffer** (a render target). `CheckDeviceFormatConversion` says "allowed", the
actual call refuses. Never plan an NV12→RGB offscreen intermediate; go straight to the
backbuffer, or use a texture + shader (unnecessary here).

## 3. Crash isolation: the exact failing call is named

The v4 six-way split of `updatesurf` did its job. Per sub-step (identical on x64 and x86):

| Sub-step | Operation | Result |
|---|---|---|
| sub0 | `CreateOffscreenPlainSurface` NV12 SYSTEMMEM | S_OK |
| sub1 | + `CreateOffscreenPlainSurface` NV12 DEFAULT | S_OK |
| sub2 | + `LockRect` on the SYSTEMMEM surface | S_OK, `pBits != NULL`, **pitch = 1920** |
| **sub3** | **+ fill the locked buffer with pixel data** | **`0xC0000005 ACCESS_VIOLATION`** |
| sub4 | + `UnlockRect` (includes the fill) | `0xC0000005` (crash inherited from the fill) |
| sub5 | + `UpdateSurface` (includes the fill) | `0xC0000005` (crash inherited from the fill) |

**The fatal operation is the CPU-side write into the locked SYSTEMMEM NV12 buffer — the
driver dies before `UpdateSurface` is ever reached.** Most probable mechanism: the driver
reports `pitch = 1920` for a 960-wide NV12 system-memory surface (2 bytes/px, as if it
were YUY2). A caller that trusts the reported pitch sizes its fill as
`pitch × height × 1.5 = 1 555 200 B`, while the backing allocation is plausibly
`width × height × 1.5 = 777 600 B`; the fill then runs off the end → AV. Whether the
allocation or the pitch report is the buggy side cannot be distinguished from outside,
and it does not matter:

> **RULE: never create, lock, fill, or `UpdateSurface` a SYSTEMMEM NV12 surface on this
> driver.** The path "decoder writes to system memory, `UpdateSurface` uploads it" is
> permanently dead (this confirms and refines the v3 finding, which could only blame
> `UpdateSurface` itself).

**Correction to `T4_skrot.txt`:** its recommended-path sentence still contains the
parenthetical "(albo SYSTEMMEM + UpdateSurface)" / "(or SYSTEMMEM + UpdateSurface)".
That half is disproved by sub3. DEFAULT-pool only.

## 4. Remaining unknown in the video path (one item)

Everything the production video loop does is now measured **except one operation**: writing
decoded pixels into a **locked DEFAULT NV12 surface** (lock itself: verified OK, pitch 960;
the benches presented 200× from DEFAULT NV12 sources without crashing, but possibly
without ever filling them). On Intel UMA this is an ordinary RAM write and the risk is low,
but the SYSTEMMEM surprise in §3 is exactly why we verify instead of assume.

→ **Stage-1 milestone 0:** `knvstd --selftest=d3d.present` (isolated process, per §7.9)
must perform *create DEFAULT NV12 → lock → fill every byte → unlock → StretchRect →
Present* once, and only then may the 10-minute G1 loopback run start.

## 5. D7 — final presentation fallback chain (settled, evidence-based)

Probed once at session start; on any refusal or AV, degrade **permanently** (never retry
the failing operation):

1. **NV12 (`D3DPOOL_DEFAULT`) → `StretchRect(D3DTEXF_LINEAR)` → backbuffer.**
   Verified S_OK scaled and 1:1; 3.0 ms. The primary and expected-to-stay path.
   Decoder writes NV12 directly into the locked DEFAULT surface.
2. **YUY2 → `StretchRect` → backbuffer.** Conversion allowed and call verified S_OK.
   Costs +12.1 ms/frame of CPU CSC (T1) — emergency use only.
3. **X8R8G8B8 → `StretchRect` → backbuffer.** Verified S_OK; CPU CSC +5.6 ms/frame (T1).
4. **GDI `SetDIBitsToDevice`.** Verified 1.9 ms; last resort if the D3D9 device is lost
   beyond recovery.

Standing rules (unchanged, now with evidence): `CheckDeviceFormatConversion` before every
`StretchRect`; on refusal skip the rung; on `0xC0000005` degrade permanently; no
format-conversion destination other than the backbuffer; no SYSTEMMEM NV12 anywhere;
letterbox 1:1 (720p video → (0,40)-(1280,760) dest rect in the 1280×800 window — actually
zero scaling needed at 720p: dest rect (0,40,1280,720)).
